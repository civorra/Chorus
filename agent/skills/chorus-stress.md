# Skill — chorus-stress

> **Trigger:** `chorus-stress <sandbox-name> [--slots <s1,s2,...>] [--families <f1,f2,...>] [--out <dir>]`
> **Agent:** `architect`
>
> `<sandbox-name>` : sandbox with a KB produced by `chorus-feed` and infrastructure generated by `chorus-check`
> `--slots <s1,s2,...>` : restrict stress generation to the listed slots only (comma-separated, optional)
> `--families <f1,f2,...>` : restrict to specific test families — `boundary` | `missing` | `edge` | `cascade` | `qualifier`
>   (default: all five families)
> `--out <dir>` : output directory for generated stress files (default: `$SANDBOX/`)
>
> ⚠️ **`--out` and `chorus-check --all` compatibility:** `chorus-check --all` discovers
> `projet-*.json` files only in `$SANDBOX/` (not in subdirectories). If `--out` points to
> a subdirectory (e.g. `$SANDBOX/stress/`), generated files will **not** be picked up by
> `--all`. Use the default `$SANDBOX/` unless you intend to run stress files manually.
> The naming convention (`projet-stress-*.json`) keeps them distinguishable from typical files.
>
> **Single responsibility: generate a suite of boundary, missing-slot, edge-combination,
> cascade, and qualifier stress-test project JSON files whose expected results are computed
> deterministically from the KB threshold tables — not inferred by the LLM.**
>
> This skill complements `chorus-create-project --batch` (which generates *typical* cases)
> by generating *adversarial* cases that expose threshold precision errors, missing
> `_DEFAULT`/`_NEEDED` handling, rare normative combinations, broken `_AFTER` propagation
> chains, and qualifier-sensitive rules.
>
> **Distinction from `chorus-create-project --strategy edges`:**
> Both target boundary values, but they differ in method and scope:
>
> | | `--strategy edges` | `chorus-stress --families boundary` |
> |---|---|---|
> | Expected results | LLM-inferred from KB | Deterministic from threshold_registry |
> | Output | One multi-element file (`projet-edges.json`) | One file per (slot × variant) |
> | Direction source | KB prose | YAML `CONDITION` operator (exact Perl comparison) |
> | Uncertain handling | None | `_expected_uncertain` flag + manifest |
>
> Run both: `edges` validates coverage breadth; `stress boundary` validates threshold precision.
>
> **Key invariant:** every `_resultats_attendus` field in every generated file is computed
> mechanically from the `threshold_registry` built in Phase 0 — never by LLM judgment.
> If a result cannot be determined mechanically, the element is flagged `_expected_uncertain: true`
> and excluded from automated convergence checking.
>
> Prerequisites:
> - `chorus-feed <sandbox-name>` must have been run (org KB + YAML rules present)
> - `chorus-check <sandbox-name> <any-project>` must have been run at least once (infrastructure present)
> - `chorus-create-project <sandbox-name> --batch` should have been run first — stress complements, never replaces, the standard suite

> ⚠️ **Sources — strict order:**
> 1. `$SANDBOX/agent/chorus/index.org` → Frame types, pipeline, namespace
> 2. `$SANDBOX/agent/chorus/<slug>.org` → `Helpers Perl` section (thresholds), `Dictionnaire des slots` (types, domains), `Catalogue des Frames` (mandatory slots), `Contraintes & Pitfalls`
> 3. `$SANDBOX/rules/<slug>/*.yml` → `CONDITION`/`PREMISSES` expressions for threshold direction extraction
>
> ⛔ **Never read** `Helpers.pm`, `Feed.pm`, `Agent/*.pm`, `Expert.pm`, `run.pl`
> ⛔ **Never guess threshold values** — extract them exactly from the org KB `Helpers Perl` section.
>   A stress project with incorrect expected results produces false discordances that mislead `chorus-strengthen`.

## Phase 0 — Read the KB and build the threshold registry

### 0.0 Sandbox inventory (first tool call — token keepalive)

**Before reading any file**, read `$SANDBOX/` directory tree (max_depth=3).

Confirm:
- `$SANDBOX/.chorus-wip.md` → **if present, stop immediately**:
  ```
  ⛔ A previous chorus-stress run was interrupted ($SANDBOX/.chorus-wip.md present).
     Review or delete the file manually, then re-run chorus-stress.
  ```
- `$SANDBOX/run.pl` → infrastructure present; if absent → stop: `⛔ Run chorus-check <sandbox-name> <any-project> first.`
- `$SANDBOX/agent/.kb-hash` → hash present (infrastructure up to date with current KB)
- `$SANDBOX/projet-*.json` → standard suite exists; if absent → warn (not a hard stop):
  ```
  ⚠️ No standard projet-*.json found. chorus-stress will run, but results are most
     meaningful when combined with chorus-create-project --batch.
  ```
- List of `<slug>.org` files and `rules/<slug>/` directories
- `$SANDBOX/stress-manifest.org` → **if present, compare its `#+KB_HASH:` header** against
  the current content of `$SANDBOX/agent/.kb-hash`:
  - **Match** → stress suite is aligned with the current KB. Continue.
  - **Mismatch** → KB was enriched since the last `chorus-stress` run. Warn and continue:
    ```
    ⚠️ KB enriched since the last chorus-stress run (hash mismatch in stress-manifest.org).
       Existing projet-stress-*.json files may test outdated threshold values.
       Recommended: re-run chorus-stress <sandbox-name> [--families boundary] to refresh.
    ```
  - **Manifest absent** → first run, no check needed.

### 0.1 Pipeline index

Read `$SANDBOX/agent/chorus/index.org`:
- Perl namespace
- Ordered agent list (slug, module, position)
- Termination agent (last position)
- Global slot dictionary if present

### 0.2 KB per agent — threshold and slot extraction

For each agent in pipeline order, apply this two-step sequence:

**Step 1 — Read** `$SANDBOX/agent/chorus/<slug>.org`:

| KB section | What to extract |
|---|---|
| `Helpers Perl` | All numeric thresholds: slot name, threshold value, boundary direction (`>=`/`>`/`<=`/`<`), corpus source reference |
| `Dictionnaire des slots` | Slot names, value type (float/int/enum/bool/string), valid domain (list of admitted values for enums) |
| `Catalogue des Frames` | Mandatory slots per `type_element`; which slots have `_DEFAULT` or `_NEEDED` annotations |
| `Slots de ciblage` | Targeting slot(s) — must be present in every generated element |
| `Contraintes & Pitfalls` | Documented edge cases and rare combinations — primary input for Family 3 (edge) |
| `Procedural attachments` | `_AFTER` trigger slots and their propagation targets — input for Family 4 (cascade) |

**Step 2 — Immediately after** (no thinking between): read `$SANDBOX/rules/<slug>/` directory tree,
then read each `.yml` file and extract:
- `CONDITION` expressions → numeric comparisons for threshold direction confirmation
- `EXCEPTION: defined $f->{slot}` → idempotence guards (slots written by this agent)
- `FIND`/`CHERCHER` `attribut:` field → confirm `type_element` canonical name

> **`type_element` guard:** if the org KB and any YAML use different names for the
> element type slot → stop immediately and report before generating any file.
> (Same check as `chorus-create-project` — see that skill for the error message template.)

### 0.3 Build the threshold registry

Aggregate all extracted data into an internal structure (not written to disk):

```
threshold_registry[slot_name] = {
  type:             float | int | enum | bool | string,
  thresholds:       [ { value: N, direction: '>='|'>'|'<='|'<',
                        verdict_above: CONFORME | NON_CONFORME,
                        source: '§N — <corpus> — <section title>',
                        agent:  '<slug>' } ],
  domain:           ['val1', 'val2', ...] | null,    # enum values
  mandatory:        true | false,
  has_default:      true | false,                    # _DEFAULT present in org KB
  has_needed:       true | false,                    # _NEEDED present in org KB
  after_triggers:   ['target_slot_1', ...],          # slots this slot triggers via _AFTER
  qualifier_for:    'slot_name' | null,              # this slot qualifies another slot's value
}
```

If `--slots` is specified → filter `threshold_registry` to the listed slots only, keeping
all slots required for mandatory-slot completeness in Family 2.

If `--families` is specified → record which families to skip in Phase 1.

## Phase 1 — Plan the stress suite

For each non-skipped family, build a generation plan before writing any file.

### Family 1 — `boundary` : values at numeric threshold boundaries

For each slot with `thresholds` in `threshold_registry`:

For each threshold `T` with direction `>=` and `verdict_above: CONFORME`:
```
→ ...-exact.json  : value = T       → expected CONFORME   (at boundary, inclusive)
→ ...-below.json  : value = T - ε   → expected NON_CONFORME
→ ...-above.json  : value = T + ε   → expected CONFORME
```

For direction `>` (strict):
```
→ ...-exact.json  : value = T       → expected NON_CONFORME (boundary excluded)
→ ...-below.json  : value = T - ε   → expected NON_CONFORME
→ ...-above.json  : value = T + ε   → expected CONFORME
```

ε rule:
- float slot, `T < 1000`  → `ε = 0.1`
- float slot, `T ≥ 1000`  → `ε = min(0.01 × T, 1.0)` (grows with T, capped to avoid coarse jumps)
- int slot                → `ε = 1`
- Document chosen ε in `_stress_note`

> ⚠️ **Extract direction from YAML CONDITION, not from KB prose.** The KB Helpers section
> documents the threshold value; the YAML CONDITION contains the exact Perl comparison operator.
> If the two disagree → flag as `_expected_uncertain: true` and report the discrepancy.

### Family 1 — optional sub-step: compound boundary (multi-slot conditions)

> **Skip condition:** if no YAML `CONDITION` expression contains comparisons on two or
> more distinct numeric slots simultaneously (e.g. `$f->{eGFR} < 60 && $f->{UACR} > 300`),
> skip this sub-step entirely. Print: `[Family 1 compound] No multi-slot conditions detected — skipped.`

During Phase 0.2, while reading each `.yml` CONDITION, flag rules where the expression
contains **two or more** numeric comparisons on **distinct** slots:

```
compound_rules = [ { agent, rule_id, slots: [(s1, T1, op1), (s2, T2, op2), ...] } ]
```

For each compound rule, generate one additional element with **all tested slots
simultaneously at their exact threshold values** (T1, T2, …):

```
→ ...-boundary-compound-<R0N>-<agent>.json :
    all slots s1=T1, s2=T2, ...  (exact thresholds simultaneously)
    _expected_uncertain: true    (AND/OR semantics may not resolve deterministically)
    _stress_note: "Compound boundary: rule <R0N> — all slots at threshold simultaneously.
                   Verify: does the rule fire when ALL conditions are exactly at boundary?"
```

> These elements are always flagged `_expected_uncertain: true` — the compound predicate
> outcome at exact boundary depends on AND/OR operator precedence and Perl evaluation order,
> which cannot be resolved from `threshold_registry` alone.
> They are valuable for manual review: a rule that fires correctly on each slot independently
> may still fail when multiple thresholds are hit at once.

### Family 2 — `missing` : one mandatory slot absent per element

For each mandatory slot M (where `threshold_registry[M].mandatory == true`):

```
→ ...-missing-<slot>.json :
    element with ALL mandatory slots present EXCEPT M
    expected result:
      has_default == true  → CONFORME (default applied automatically)
      has_needed == true   → CONFORME if derivation condition met (document condition in _stress_note)
                           → flag _expected_uncertain: true if derivation condition cannot be determined
      otherwise            → element rejected by Feed (unprocessed) OR NON_CONFORME per rules
```

> ⚠️ A stress element that expects NON_CONFORME for a missing slot that has `_DEFAULT`
> will always produce a false discordance. Check `has_default` and `has_needed` before
> setting the expected result — this is the most common source of incorrect stress files.

### Family 3 — `edge` : rare but normatively valid combinations

For each documented edge case in `Contraintes & Pitfalls` AND for each pair of slots
(s1, s2) where s1 is in its CONFORME range but s2 is NON_CONFORME (overall verdict
is NON_CONFORME despite s1 looking fine):

```
→ ...-edge-<s1>-<s2>.json :
    element with s1 in CONFORME range AND s2 in NON_CONFORME range
    → expected NON_CONFORME (s2 dominates)
    → _stress_note: "counter-intuitive — good <s1> does not compensate bad <s2>"
```

Also generate one element for each combination documented in `Contraintes & Pitfalls`
with a note referencing the corpus section that defines this edge case.

Skip this family if no edge combinations are documented in any agent KB and no
cross-slot interactions are visible in the pipeline.

### Family 4 — `cascade` : `_AFTER` propagation chains

For each slot with non-empty `after_triggers` in `threshold_registry`:

```
→ ...-cascade-<slot>.json :
    element where <slot> is set to a value that triggers _AFTER
    → expected (presence check — always deterministic):
        each slot in after_triggers must be PRESENT in the pipeline output
        if a propagated slot is ABSENT → _AFTER hook broken or Feed.pm not registering it
    → expected (value check — only if formula is in the KB org):
        if the KB org `Slot dictionary` documents the propagation formula explicitly
        (e.g. "Triggers besoin_thermique = 1 when classe_conductivite ∈ {A, B}")
        → add the expected value to _resultats_attendus for that propagated slot
        if the formula is NOT in the KB org → set _expected_uncertain: true for the value
        (presence is still checked deterministically; only the value is uncertain)
    → _stress_note: "tests _AFTER propagation: <slot> → <target_slot_1>, <target_slot_2>
                     presence: deterministic / value: <certain|uncertain — formula not in KB org>"
```

> **This family tests the procedural KB**, not the declarative rules.
> A cascade discordance points to a broken Helper, a missing `_AFTER` registration in Feed.pm,
> or an incorrect value in a normative table. It is the most diagnostic family for Helpers.pm bugs.
>
> **Presence vs value — key distinction:**
> | Check | Deterministic? | Source |
> |---|---|---|
> | Propagated slot is present after run | ✅ always | `after_triggers` list in `threshold_registry` |
> | Propagated slot has the correct value | 🟠 only if formula in KB org | KB org `Slot dictionary` `Triggers` annotation |
>
> Never read `Feed.pm` to recover the formula — if it is absent from the KB org,
> the value check is flagged uncertain. This is intentional: a missing formula in the KB org
> is itself a documentation gap worth surfacing.

Skip this family silently if no slot has non-empty `after_triggers`.

### Family 5 — `qualifier` : same value, different qualifier

Applicable only when the KB contains explicit qualifier slots — slots whose value modifies
the strength of evidence for another slot (e.g. IUCN `reduction_qualifier`: observed/estimated/inferred/suspected;
KDIGO `mature_individuals_qualifier`: exact/estimated/range).

```
→ ...-qualifier-<slot>-<qualifier_a>.json
→ ...-qualifier-<slot>-<qualifier_b>.json
    identical numeric value on the primary slot, different qualifier value
    expected result:
      if qualifier affects verdict → document both expected results and difference
      if qualifier is verdict-invariant → mark both _stress_note: "qualifier-invariant — same verdict"
```

Skip this family silently if no qualifier slot exists in `threshold_registry`.

## Phase 2 — Compute expected results

**For every planned element**, compute `_resultats_attendus` mechanically
before generating any JSON:

```
for each element E:
  1. Apply threshold_registry in pipeline order
  2. For each agent, for each slot with thresholds:
       evaluate E[slot] against each threshold
       → assign per-agent per-slot verdict
  3. Aggregate across agents → final status
  4. Assign _resultats_attendus: { result_slot: verdict, ... }
  5. If any step is ambiguous → set _expected_uncertain: true
     and document the ambiguity in _stress_note
```

> **When to flag `_expected_uncertain: true` — mandatory checklist:**
> Flag an element uncertain if ANY of the following applies:
>
> | Situation | Why the registry is insufficient |
> |---|---|
> | The slot appears in a multi-condition `AND`/`OR` CONDITION expression (e.g. `eGFR < 60 AND UACR > 300`) | Whether the compound predicate fires depends on the other slot's value — cannot be resolved from a single-slot threshold |
> | A rule's `EXCEPTION` guard references a slot written by a **different** agent (earlier in the pipeline) | Whether the guard fires depends on upstream execution order, not just thresholds |
> | The slot is consumed only **after** inter-agent propagation (agent A writes to BOARD → agent B reads it) | The value seen by the rule is a BOARD-mediated result, not the project-JSON input |
> | The CONDITION combines a numeric threshold **and** an enum/bool check on another slot | The second check may override the numeric verdict without a deterministic rule in the registry |
>
> ⛔ **Never use LLM judgment to resolve ambiguity.** If the expected result cannot be
> determined purely from `threshold_registry`, set `_expected_uncertain: true` and move on.
> Uncertain elements are still generated (they are useful for manual review) but are
> excluded from automated convergence checking by `chorus-check --all`.
>
> ⚠️ **Downstream impact of uncertain elements:** `chorus-strengthen` will classify
> discordances from uncertain elements as real gaps unless explicitly filtered.
> Always cross-reference the `stress-manifest.org` uncertain list before acting on
> any gap reported by `chorus-strengthen` on a `projet-stress-*.json` file.

## Phase 3 — Generate stress project files

### 3.0 — Create WIP checkpoint

**Before writing any file**, create `$SANDBOX/.chorus-wip.md`:

```markdown
# chorus-stress WIP checkpoint
sandbox: <name>
families: <comma-separated list of families being generated>
started: <YYYY-MM-DD>
status: IN_PROGRESS
```

> Presence = stress generation incomplete. Absence = clean state.
> If `.chorus-wip.md` is already present when this skill starts → stop and warn:
> ```
> ⛔ A previous chorus-stress run was interrupted ($SANDBOX/.chorus-wip.md present).
>    Review or delete the file, then re-run chorus-stress.
> ```

### 3.1 — Write stress files

**One JSON file per stress element** (not grouped — one file = one focused test case):

```json
{
  "projet": "stress-<family>-<slot>-<variant>",
  "description": "<one-line human-readable description of what this test exercises>",
  "_stress": {
    "family":             "boundary",
    "slot":               "<slot_name>",
    "threshold":          60.0,
    "direction":          ">=",
    "epsilon":            0.1,
    "source":             "KDIGO 2024 Table 2 §S137",
    "agent":              "<slug>",
    "expected_uncertain": false
  },
  "elements": [
    {
      "id":                  "<TYPE>-STRESS-<FAMILY>-<SLOT>-<VARIANT>",
      "type_element":        "<type_element>",
      "<targeting_slot>":    "<value>",
      "<tested_slot>":       <boundary_value>,
      "<other_mandatory_1>": <valid_value>,
      "<other_mandatory_2>": <valid_value>,
      "_resultats_attendus": {
        "<result_slot>": "<CONFORME|NON_CONFORME>"
      },
      "_stress_note":        "<explanation of why this verdict is expected>",
      "_expected_uncertain": false
    }
  ]
}
```

### File naming convention

```
projet-stress-<family>-<slot>-<variant>.json
```

Examples:
```
projet-stress-boundary-eGFR-60-exact.json
projet-stress-boundary-eGFR-60-below.json
projet-stress-boundary-UACR-30-above.json
projet-stress-missing-eGFR.json
projet-stress-missing-UACR.json
projet-stress-edge-G4-A1.json
projet-stress-edge-G2-A3.json
projet-stress-cascade-ckd-stage.json
projet-stress-qualifier-reduction-observed.json
projet-stress-qualifier-reduction-inferred.json
```

### Element ID convention

```
<TYPE>-STRESS-<FAMILY>-<SLOT>-<VARIANT>
```

Examples:
```
CKD-STRESS-BOUNDARY-eGFR-60-EXACT
CKD-STRESS-MISSING-UACR
CKD-STRESS-EDGE-G4-A1
SP-STRESS-CASCADE-ckd-stage
SP-STRESS-QUALIFIER-reduction-OBSERVED
```

> **ID stability rule:** IDs must be stable across regenerations of the same stress suite.
> Use deterministic conventions only — never timestamps or random suffixes.
> This allows `chorus-check --all` runs to be compared diff-style across KB iterations.

### Mandatory slots rule

Every stress element must include ALL mandatory slots from `threshold_registry`
EXCEPT the one intentionally omitted in Family 2. For all other families,
missing a mandatory slot would make the element unprocessed by Feed — masking
the actual stress condition being tested.

Set all non-tested mandatory slots to valid mid-range values that do not
trigger any other rule (to isolate the stress condition).

## Separation of responsibilities

| | `chorus-create-project` | `chorus-stress` | `chorus-strengthen` |
|---|---|---|---|
| **Reads** | org KB | org KB + YAML CONDITIONs | pipeline output + org KB |
| **Generates** | Typical project JSON | Boundary/edge/cascade project JSON | Gap report + enrichment roadmap |
| **Expected results** | LLM + KB inference | **Deterministic from threshold_registry** | N/A |
| **Modifies KB** | ✗ | ✗ | ✗ |
| **Tests** | Rule variety and coverage | **Threshold precision, _DEFAULT/_NEEDED, _AFTER** | Gap classification |
| **Triggered** | After `chorus-feed` | After `--batch`, before `--all` | After failed `--all` |

## Integration in the convergence loop

```
chorus-feed <sb> <corpus>              ← generate KB
chorus-check <sb> <project>            ← generate infrastructure
chorus-create-project <sb> --batch     ← typical cases (4 files)
chorus-stress <sb>                     ← boundary + edge + cascade cases  ← THIS SKILL
chorus-check <sb> --all                ← validate both suites
chorus-strengthen <sb>                 ← diagnose remaining gaps
[targeted YAML / Helper corrections]
chorus-check <sb> --all                ← re-validate
chorus-strengthen <sb>                 ← convergence check
✅ CONVERGED on ALL suites (typical + stress, 0 discordances, 0 unprocessed)
```

**Convergence on both suites guarantees:**
- Every YAML rule fires correctly in isolation and in interaction
- Every numeric threshold in the Helpers is encoded with the correct value and direction
- `_DEFAULT` and `_NEEDED` handle missing slots as documented in the org KB
- `_AFTER` propagation chains produce the expected downstream slot values
- Qualifier-sensitive rules discriminate correctly when qualifiers differ

**Convergence does NOT guarantee:**
- Corpus coverage (every normative article is covered by a rule) → use `chorus-review-kb`
- Absence of `_ISA` cycles → static structural validation (not covered by any current skill)
- Org KB ↔ `Helpers.pm` parity → see `chorus-feed` Helpers Checklist, `chorus-check` Phase 2.5
