* Cycle de vie de la page
  :PROPERTIES:
  :CATEGORY: Architecture
  :END:

Le script est chargé *mi-page* (entre les divs principales et les overlays
settings), sans =defer=. Séquence d'exécution au chargement :

#+begin_src
1. init()                  — renderGlobalDashboard() + renderSidebar()
2. bootServices()          — démarre le ping ECA, active les status pills
3. loadSettingsFromStorage() — applique thème/densité depuis localStorage
4. initFromServer()        — GET /api/scan → remplace les données PoC
                             par les vraies données serveur ;
                             re-render dashboard + sidebar si OK.
                             Mode simulation silencieux si le serveur
                             ne répond pas (console.warn uniquement).
#+end_src

* Pattern SSE (Server-Sent Events)
  :PROPERTIES:
  :CATEGORY: Architecture
  :SOURCE: chorus-web.js §GENERIC ECA TERMINAL (l.3239)
  :END:

L'ensemble des opérations longues (terminal ECA, pipeline run, import)
utilisent SSE via =EventSource= :

#+begin_src js
// Ouverture
const es = new EventSource(`${API}/api/terminal/${sessionId}/stream`);

// Événements reçus
es.addEventListener('chunk',   e => append(JSON.parse(e.data).content));
es.addEventListener('done',    e => finish());
es.addEventListener('error',   e => handleError());
es.onerror = () => tryReconnect();

// Fermeture propre
es.close();
#+end_src

Le backend envoie =data: <json>\n\n= pour chaque chunk, =event: done= en fin.
Le DOM ring buffer (=// ─── DOM RING BUFFER ───=) limite le nombre
de nœuds affichés pour éviter les fuites mémoire sur les sessions longues.

** ⚠️ Bug Jetty eca-server — contournement SSE + TCP-only health-check (2026-10-14)
   :PROPERTIES:
   :SOURCE: eca-client.js (commit 7e76478)
   :END:

=eca-server= (Jetty 12 / binaire natif GraalVM) lève une
=IllegalArgumentException= ("No matching field found: getOutputStream...")
sur plusieurs endpoints HTTP dès qu'un chat détient du contenu — sans
impact fonctionnel côté client (réponse toujours obtenue via les fallbacks/
SSE existants) mais pollue fortement les logs =eca-server=.

- =promptAndWaitSSE()= — alternative à l'ancien =promptAndWait()= (polling
  =GET /api/v1/chats/:id=, déclencheur principal du bug), construite sur
  =subscribeEcaEvents()= (=GET /api/v1/events=, déjà utilisé par le terminal
  sans être affecté). Prompt one-shot → texte complet, aucun polling.
- =pingTcp()= — probe de connexion TCP pure (aucune requête HTTP) pour
  vérifier la joignabilité d'=eca-server= sans jamais passer par sa couche
  HTTP buguée.

  :PROPERTIES:
  :CATEGORY: Architecture
  :END:

Pas de router dédié — navigation par manipulation de classes =active= sur
les divs =.page=. Trois pages principales :

| ID DOM | Page | Activée par |
|---|---|---|
| =#page-global= | Dashboard global | =goHome()=, init |

* Import — routage via session ECA headless (2026-10-14)
  :PROPERTIES:
  :CATEGORY: Architecture
  :SOURCE: server/routes/projects.js
  :END:

⚠️ L'ancien pipeline d'import =POST /api/projects/.../import= invoquait
=spawnPerl(['chorus-import-project.pl', ...])= — un script **qui n'a jamais
existé** dans le repo (placeholder MVP0 jamais implémenté). La route
d'import n'a donc **jamais réellement fonctionné** avant le commit =387b103=.

La véritable implémentation de =chorus-import-project= est un skill ECA
(=Engine/agent/skills/chorus-import-project.md=), invocable uniquement via
une session de chat ECA headless — pas un process Perl autonome.

Nouveau pattern (repris de =server/routes/terminal.js=) :
- chat dédié =eca-import-<sbId>-<projId>=
- =subscribeEcaEvents()= pour le streaming SSE
- routage explicite vers l'agent =code=
- stratégie anti-race "fire-and-forget prompt + ~200ms delay + setChatAgent"
  pour les chats neufs (identique à =terminal.js=)
- timeout configurable (15 min par défaut, borné 1 min–4h) + heartbeat
- protocole de complétion =DONE=

Les routes =/run=, =/check=, =/chat=, =/run-report= restent inchangées
(=spawnPerl= toujours utilisé par =/run= pour le vrai script =run.pl=).
