* PITFALL _APPLY called as coderef, not via Frame dispatch
  :PROPERTIES:
  :COMPONENT: Chorus::Engine
  :SEVERITY: Critical
  :FIXED_IN:  2.01
  :END:

Before v2.01, =applyrules()= called =_APPLY= via Frame dispatch (=$rule->_APPLY=),
which triggered =pushself($rule)= and caused =$SELF= to point to the rule Frame
throughout the entire ACTION execution.

Consequence: =$SELF->solved()=, =$SELF->cut()=, etc. inside a YAML =ACTION:= block
were silent no-ops — the rule Frame does not inherit these methods.

** Fix applied
=_APPLY= is now called as a plain coderef:
#+begin_src perl
my $_af = $rule->{_APPLY};
$res = $_af ? $_af->(%opt) : 0;
#+end_src
=$SELF= stays on the engine throughout the ACTION. Both syntaxes are now equivalent:
#+begin_src yaml
TERMINAL: solved          # engine-level, after _APPLY returns
#+end_src
#+begin_src yaml
ACTION: |
  $SELF->solved() if ...  # inline, can be conditional
#+end_src

** Rule
Never call =$SELF->solved()= assuming =$SELF= is the rule —
=$SELF= is always the engine inside an ACTION block.

* PITFALL _PREMISSES declared in YAML but ignored by applyrules()
  :PROPERTIES:
  :COMPONENT: Chorus::Engine
  :SEVERITY: Surprising
  :ADR:      ADR-001
  :END:

=PREMISSES:= / =PREMISES:= in a YAML file is compiled into =_PREMISSES => {...}=
on the rule Frame. =applyrules()= **does nothing with it**.

It is only available as metadata for =reorder()=:
#+begin_src perl
$agent->reorder(sub {
    my ($r1, $r2) = @_;
    return -1 if $r1->{_PREMISSES}{prioritaire};
    return  1 if $r2->{_PREMISSES}{prioritaire};
    return  0;
});
#+end_src

** Rule
=PREMISES= = a boolean tag system on rules (=slot => 'Y'=), readable only
by a comparator passed to =reorder()=.
Outside a =reorder()= call: omit =PREMISES= entirely — it is completely inert.
Prerequisite logic (trigger conditions) belongs in =CONDITION=.
See =lib/Chorus/Engine.pm §codeRule()= · =chorus-engine-yaml.md §PREMISES= · ADR-001.

* PITFALL _MAX_ITER silently ignored by Chorus::Expert->new()
  :PROPERTIES:
  :COMPONENT: Chorus::Expert
  :SEVERITY: Silent
  :END:

=Chorus::Expert->new()= ignores all its arguments. Passing =_MAX_ITER= to the
constructor does nothing — the value is silently discarded.

** Correct syntax
#+begin_src perl
my $xprt = Chorus::Expert->new();
$xprt->{_MAX_ITER} = 50_000;   # always via direct assignment
#+end_src

The default is =10_000= iterations (outer loop of =process()=),
distinct from =_MAX_CYCLES= (inner loop of =loop()=, default =10_000= cycles).

** Heuristic rule
For a pipeline of N frames × M total rules:
=_MAX_ITER= ≥ N × M × 10 (safety margin).

* PITFALL Multiple CONDITION: implicit OR (not AND)
  :PROPERTIES:
  :COMPONENT: Chorus::Engine / DSL YAML
  :SEVERITY: Counter-intuitive
  :ADR:      ADR-002
  :END:

When =CONDITION:= contains a YAML list:
#+begin_src yaml
CONDITION:
  - "$f->{type} eq 'stud'"
  - "defined $f->{section}"
#+end_src

The conditions are joined with =or= (implicit OR) — the rule fires if **any one**
condition is true. =setCondition()= performs the join:
#+begin_src perl
return join("\n      or ", map { $SELF->codeCondition($_) } @$c);
#+end_src

For AND, put everything in a single string:
#+begin_src yaml
CONDITION: "($f->{type}//'') eq 'stud' && defined $f->{section}"
#+end_src

* PITFALL Multiple filtre: implicit AND (opposite of CONDITION)
  :PROPERTIES:
  :COMPONENT: Chorus::Engine / DSL YAML
  :SEVERITY: Asymmetric
  :ADR:      ADR-002
  :END:

=filtre:= inside a =CHERCHER:= / =FIND:= block uses =setFilter()= which joins
expressions with =and= (implicit AND) — unlike =CONDITION:= which is OR.

#+begin_src yaml
FIND:
  f:
    attribut: needs_domain
    filtre:
      - "($_{type_element}//'') =~ /stud/"
      - "defined $_{stud_spacing_mm}"
#+end_src

Both filters are AND'd. This is intentional (restrictive pre-filtering of scope).

* PITFALL FILTRE-SEQUENCE-LITERAL — filtre YAML sequence of literal values
  :PROPERTIES:
  :COMPONENT: Chorus::Engine / DSL YAML
  :SEVERITY: Critical — silent
  :DISCOVERED: 2026-11-14 (chorus-audit-rules sandbox 03b-contruction-bois-HABITATION)
  :ENG: ENG-050
  :END:

Declaring =filtre:= as a YAML sequence of literal values (not Perl expressions)
generates a constant truthy filter — the filter is completely inoperative.

#+begin_src yaml
# ⛔ WRONG — YAML sequence → arrayref of barewords → grep { cheminement_ext } = truthy
CHERCHER:
  ce:
    attribut: type_element
    filtre:
      - cheminement_ext
      - cheminement_int
#+end_src

=setFilter()= expects *Perl expressions* in the array (combined with AND), not literal
values to compare against. The arrayref =["cheminement_ext", "cheminement_int"]= compiles to:

: grep { cheminement_ext and cheminement_int } fmatch(slot => 'type_element')

Both barewords are non-empty → always truthy → all Frames carrying the =type_element=
slot enter the scope regardless of their actual value.

No error is raised. =loadRules()= emits a =FILTRE-SEQUENCE-LITERAL= warning
(implemented in ENG-050 Axe A, =_check_filtre_not_string()=).

** Rule
=filtre:= must *always* be a quoted Perl string operating on =$_=.

#+begin_src yaml
# ✅ CORRECT — single value
filtre: '$_->{type_element} eq "cheminement_ext"'

# ✅ CORRECT — multiple values
filtre: '$_->{type_element} =~ /^(cheminement_ext|cheminement_int)$/'

# ✅ CORRECT — array of real Perl expressions (implicit AND)
filtre:
  - '$_->{type_element} =~ /^cheminement/'
  - 'defined $_->{largeur_m}'
#+end_src

Discovered on 7 rules of sandbox =03b-contruction-bois-HABITATION= (agent-accessibilite-pmr
R01–R07) — filters targeted distinct PMR types but let all =type_element= Frames through,
producing incorrect verdicts on unrelated types.

* PITFALL fmatch() cannot see slots set after new()
  :PROPERTIES:
  :COMPONENT: Chorus::Frame / fmatch
  :SEVERITY: Subtle
  :END:

=%REPOSITORY= is updated by =set()= but not by direct hash assignment on a Frame:
#+begin_src perl
$f->{nouveau_slot} = 'valeur';   # does NOT update %REPOSITORY
$f->set('nouveau_slot', 'val');  # ✅ updates %REPOSITORY
#+end_src

=fmatch(slot => 'nouveau_slot')= will not find =$f= if the slot was set
via direct assignment.

** Rule
Always use =$f->set(...)= for any Frame modification inside rules.

* PITFALL {} passed to Chorus::Frame->new() is promoted to a Frame
  :PROPERTIES:
  :COMPONENT: Chorus::Frame
  :SEVERITY: Silent / destructive
  :DISCOVERED: 2026-07-03 (Step 3 backward-chaining)
  :END:

=Chorus::Frame->new(key => {})= — a hashref value ={}= is automatically
promoted to a =Chorus::Frame=. The slot therefore stores a Frame, not a plain hashref.

Consequence: =keys %{ $frame->{key} }= includes =_KEY= (the Frame's MD5),
causing cryptic errors such as:
#+begin_example
Can't use string ("rJOaU/xPgvoj2LwKKck41g") as an ARRAY ref
#+end_example

** Rule
Never pass ={...}= or ={}= as a value to =Chorus::Frame->new(...)=
when a plain hashref is expected. Use direct assignment **after** =new()=:

#+begin_src perl
my $res = Chorus::Frame->new(_RULES => [], @_);  # [] arrayref OK (not promoted)
$res->{_RULE_PRODUCES} = {};                     # direct assignment — stays a plain hashref
#+end_src

**Arrayrefs** (=[]=) are NOT promoted — only hashrefs are.

* PITFALL Chorus::Engine is a Frame — multiple inheritance is possible
  :PROPERTIES:
  :COMPONENT: Chorus::Engine
  :SEVERITY: Surprising but functional
  :END:

=Chorus::Engine->new()= creates a Frame that inherits from the =$ENGINE= prototype:
#+begin_src perl
sub new {
    shift;
    my $res = Chorus::Frame->new(_RULES => [], @_);
    $res->_inherits($ENGINE);    # added after construction
    return $res;
}
#+end_src

An engine instance can therefore have multiple parents (multiple inheritance), e.g.
inheriting from both =$ENGINE= and an application configuration Frame.
This is not a bug — it is intentional by design.

* PITFALL Chorus-Engine ≠ Chorus::Engine (naming confusion resolved in v2)
  :PROPERTIES:
  :COMPONENT: CPAN Distribution
  :SEVERITY: Informational
  :FIXED_IN:  2.01
  :END:

Until v2.01, the CPAN distribution was named =Chorus-Engine=, suggesting it only
contained the =Chorus::Engine= class. In reality it contains the entire platform:
=Chorus::Engine=, =Chorus::Expert=, =Chorus::Frame=, =Chorus::Collection::*=,
the YAML DSL, and agent skills.

Renamed to =Chorus= in v2.01. MetaCPAN, RT, and GitHub URLs updated accordingly.

* PITFALL _CYCLE and _SUCCES reset to 0 at each loop()
  :PROPERTIES:
  :COMPONENT: Chorus::Engine
  :SEVERITY: Misleading
  :DISCOVERED: 2026-07-24 (deep-chorus full — source Engine.pm v2.0.2)
  :END:

=loop()= always starts with:
#+begin_src perl
$SELF->{_SUCCES} = 0;
$SELF->{_CYCLE}  = 0;
#+end_src

These are **not** cumulative counters over the agent's lifetime.
=_CYCLE= holds the number of =applyrules()= passes in the **current** =loop()= call.
Between two =loop()= calls, these values are always reset to zero.

Code that reads =_CYCLE= after =loop()= to know the total cycle count
only gets the counter of the last =loop()= invocation.

** Rule
Use =_CYCLE= only as an intra-=loop()= cycle counter (e.g. in =_APPLY= to
indicate the current cycle). For a global count, accumulate in a custom BOARD slot
from within the rules.

* PITFALL BOARD->{SOLVED} and BOARD->{FAILED} cleared after process()
  :PROPERTIES:
  :COMPONENT: Chorus::Expert
  :SEVERITY: Surprising
  :DISCOVERED: 2026-07-24 (deep-chorus full — source Expert.pm v2.0.2)
  :END:

=process()= deletes these flags before returning:
#+begin_src perl
($board->delete('SOLVED'), return 1) if $board->{SOLVED};
($board->delete('FAILED'), return  ) if $board->{FAILED};
#+end_src

After =process()= returns, testing =$agent->BOARD->SOLVED= always yields
=undef= even if the pipeline succeeded.

** Correct syntax
#+begin_src perl
my $ok = $xprt->process();
if ($ok) { # pipeline solved }
else      { # failed or timeout }
#+end_src

Never rely on =BOARD->{SOLVED}= after =process()=. Domain results must be
stored in custom BOARD slots (=$agent->BOARD->set('result', ...)=) inside
the termination rule — these slots are not cleared by =process()=.

* PITFALL BOARD-ACCESS-UNDEF — $SELF->BOARD returns undef before first BOARD slot is published
  :PROPERTIES:
  :COMPONENT: Chorus::Engine / DSL YAML
  :SEVERITY: Significant — potential crash
  :DISCOVERED: 2026-11-14 (chorus-audit-rules sandbox 03b-contruction-bois-HABITATION)
  :ENG: ENG-050
  :END:

=$SELF->BOARD= returns =undef= until any agent has published a BOARD slot.
Accessing =$SELF->BOARD->{key}= without a null-check crashes with:

: Can't use an undefined value as a HASH reference

Most at-risk case: the first agent in the pipeline (pos. 1/N) accesses BOARD
in its =ACTION= on the very first cycle, before it has initialised BOARD itself.

#+begin_src perl
# ⛔ WRONG — crash if no BOARD slot exists yet
my $liste = $SELF->BOARD->{classements_resolus} // [];

# ✅ CORRECT — explicit guard in ACTION
my $b     = $SELF->BOARD // {};
my $liste = $b->{classements_resolus} // [];
#+end_src

In YAML =EXCEPTION= and =CONDITION=, the guard is even more important:

#+begin_src yaml
# ⛔ WRONG — crash if BOARD undef
EXCEPTION: defined $SELF->BOARD->{verdict_ok}

# ✅ CORRECT — null-safe
EXCEPTION: '($SELF->BOARD && defined $SELF->BOARD->{verdict_ok})'
#+end_src

#+begin_src yaml
# ⛔ WRONG — crash in CONDITION if BOARD undef
CONDITION: defined $SELF->BOARD->{phase_done}

# ✅ CORRECT
CONDITION: '($SELF->BOARD && defined $SELF->BOARD->{phase_done})'
#+end_src

** Rule
- In YAML =EXCEPTION/CONDITION=: *always* use `($SELF->BOARD && ...)` before any access.
- In YAML =ACTION=: use `my $b = $SELF->BOARD // {};` then `$b->{key}`.
- Aggregation / BOARD-publishing rules: combine null guard + key guard:
  `($SELF->BOARD && defined $SELF->BOARD->{key})`.

** Engine fix applied (ENG-050 Axe B)
=BOARD= is initialised to ={}= in =loadRules()=. =$SELF->BOARD= never returns
=undef= once the engine is loaded (unless called before =loadRules()=).

* PITFALL Pattern B (_ISA prototypes): $inject_isa called in only one pass
  :PROPERTIES:
  :COMPONENT: Feed.pm / Inter-Frame Relations
  :SEVERITY: Silent — incorrect results
  :DISCOVERED: 2026-07-23 (sandbox test-11 — feat/relations-inter-frames)
  :END:

In a Pattern B implementation (Minsky prototypes via =_ISA=), =Feed.pm= loads
elements in **two passes**:
- Pass 1: elements without a =*_ref= field (standalone elements)
- Pass 2: elements with =*_ref= (inter-frame link resolution)

If the =$inject_isa= closure (which calls =fselect= and =$frame->_inherits($proto)=)
is only called in pass 2, elements without =*_ref= never receive their prototype.
Consequence: =fmatch(slot => 'threshold_slot_X')= returns engine defaults instead
of prototype-inherited thresholds → silent false positives.

** Rule
Call =$inject_isa= in **both passes**, before link resolution.

#+begin_src perl
# Pass 1 — elements without *_ref
for my $id (grep { !$e->{$_}{supports_ref} } keys %$projet) {
    my $frame = Chorus::Frame->new(...);
    $inject_isa->($frame, $e->{$id});   # ← required here too
    ...
}
# Pass 2 — *_ref resolution + _ISA on remaining elements
for my $id (keys %$projet) {
    $inject_isa->($TYPED_FRAMES{$id}, $e->{$id});  # idempotent if already called
    ...
}
#+end_src

* PITFALL *_ref in %SLOTS_REQUIS — silent backward-compatibility break
  :PROPERTIES:
  :COMPONENT: Feed.pm / Inter-Frame Relations
  :SEVERITY: Silent breakage
  :DISCOVERED: 2026-07-23 (sandbox test-11 — feat/relations-inter-frames)
  :END:

=*_ref= fields (e.g. =supports_ref=, =building_ref=) represent **optional** inter-frame
links sourced from drawings / BIM / engineer specs.
A project JSON without these fields must remain valid.

If =Feed.pm= includes them in =%SLOTS_REQUIS=, older project JSONs will be
silently rejected with a =warn + next= at runtime.

** Absolute rule
Never add a =*_ref= field to =%SLOTS_REQUIS=.
YAML rules that use an inter-frame link must always provide a fallback (Option A)
or a skip guard (Option B):

#+begin_src yaml
# Option A — fallback to direct slot if link absent
ACTION: |
  my $target = $w->get('link_slot');
  my $val = $target ? $target->get('remote_slot') : $w->get('local_fallback_slot');
  1

# Option B — skip element if link absent
EXCEPTION: 'not defined $w->get("link_slot")'
#+end_src

* PITFALL eca__ask_user silently ignored inside a sub-agent
  :PROPERTIES:
  :COMPONENT: chorus-web / ECA terminal
  :SEVERITY: Medium (silent degradation, no error)
  :DISCOVERED: 2026-10-30
  :ADR:      ADR-017
  :END:

** Symptom
A skill running inside =eca__spawn_agent= calls =eca__ask_user= — the call
returns immediately with =""= without showing any widget to the user.
The skill continues with an empty response, producing incorrect or incomplete
results with no error signal.

** Cause
In =subscribeEcaEvents= (=eca-client.js=), events from sub-chats
(=isSubagentChat=) do not trigger the =chat:ask-question= handler:

#+begin_src javascript
if (isParentChat && eventType === 'chat:ask-question') {
  // ← this guard excludes sub-agents
}
#+end_src

The sub-agent runs in a separate chatId (=subagent-<id>=). The =chat:ask-question=
handler is only active for the parent chat. The ECA =eca__ask_user= call receives =""=
and continues without blocking.

** Affected pattern
Any skill that calls =eca__ask_user= AND may be launched via =eca__spawn_agent=.
Chorus skills affected: =chorus-strengthen= (Phase 4-checkpoint),
=chorus-feed= (Phase 6.5), =chorus-create-project= (Phase 3 --batch-seq).

** Protection in place (insufficient)
The =AUTONOMOUS_MODE= guard (=chorus-engine.md § Autonomous mode=) detects
=eca__ask_user= absent from the tool catalogue — which covers "tool unavailable"
but NOT the "tool available but sub-agent" case: the tool is present in the
sub-agent's catalogue, so =AUTONOMOUS_MODE= never triggers, =eca__ask_user=
is called → returns =""=.

** Recommended fix
Add explicit sub-agent context detection as an additional =AUTONOMOUS_MODE=
condition in each affected skill:

#+begin_src markdown
| Running inside a sub-agent | Spawned via `eca__spawn_agent` — OR —
  detect empirically: call `eca__ask_user` with a sentinel value and check
  if the return is `""` without user interaction delay |
#+end_src

Structural fix: propagate =chat:ask-question= from sub-agents to the parent terminal
(=subscribeEcaEvents= § sub-agent handling), routing the reply to the correct chatId.
Not implemented as of 2026-10-30.

** Rule
=eca__ask_user= is reliable only in the **parent** chat of a webapp ECA terminal.
Any skill potentially spawned via =eca__spawn_agent= must implement =AUTONOMOUS_MODE=
to handle the =""= return case.

* PITFALL _incomplet + required slot absent → die() in load_projet → chorus-check infinite loop
  :PROPERTIES:
  :COMPONENT: Feed.pm / chorus-templates T1
  :SEVERITY: Critical — infinite loop
  :DISCOVERED: 2026-11-12 (sandbox 02b-FI-copyright, element work-01)
  :ENG: ENG-039
  :END:

=load_projet= validates =%SLOTS_REQUIS= slots via =die()= for every element.
An element marked =_incomplet: 1= (by =chorus-audit-import=) may legitimately
have missing slots — the =die= is semantically wrong in that case.

Result: =chorus-check= enters an infinite loop (generates =Feed.pm= → =die= →
retry → =die= → ...).

** Mandatory fix in template T1 (=chorus-templates.md=)

#+begin_src perl
# ✅ CORRECT — guard _incomplet before SLOTS_REQUIS loop
unless ($elem->{_incomplet}) {
    for my $slot (@$requis) {
        die "Slot '$slot' missing for '$id' (type_element=$type_element)\n"
            unless defined $elem->{$slot};
    }
}
#+end_src

Implemented in =chorus-templates.md= template T1 (ENG-039).
Existing =Feed.pm= files on sandboxes must be regenerated via =chorus-check=.

* PITFALL return 0 without writing output slot → infinite re-fire (_incomplet rules)
  :PROPERTIES:
  :COMPONENT: Chorus YAML DSL / Rules
  :SEVERITY: Critical — silent engine loop
  :DISCOVERED: 2026-11-12 (sandbox 02b-FI-copyright, R03-copyright-term)
  :ENG: ENG-039
  :END:

A rule whose =EXCEPTION= is =defined $f->{output_slot}= must write =output_slot=
in **all** branches of its =ACTION=, including the "insufficient data" branch.
A =return 0= without writing leaves the =EXCEPTION= false →
the rule re-fires every cycle until =_MAX_ITER=.

#+begin_src yaml
# ⛔ WRONG — return 0 without writing output_slot
EXCEPTION: defined $f->{protection_status}
ACTION: |
  if (defined $author_death) {
    $f->set('protection_status', 'CONFORME');
    return 1;
  } else {
    return 0;   # ← EXCEPTION stays false → infinite re-fire
  }

# ✅ CORRECT — all branches write output_slot
ACTION: |
  if (defined $author_death) {
    $f->set('protection_status', 'CONFORME');
    return 1;
  } else {
    $f->set('protection_status',    '_a_confirmer');
    $f->set('non_conformity_motif', 'Insufficient data: author_death_year absent');
    return 1;
  }
#+end_src

Corollary: if the rule pushes to =_rule_trace= before checking data,
each re-fire adds a duplicate entry → polluted trace (Bug 3 in ENG-039).
Mandatory guard: =unless (grep { ... } @$trace)= around the push.

See =chorus-engine-yaml.md § ENG-039= for the full convention.
